# Investing Research Dashboard MVP Plan

**Goal:** Build a low-cost, deployed, JavaScript-first investing-research dashboard that lets a user search for a company/ticker, pull relevant market data, fundamentals, filings, news, financial sentiment, and a source-linked `gemini-3-flash-preview` research summary.

**MVP posture:** Informational research assistant, not investment advice, not a trading bot.  
**Frontend preference:** Real deployed JS site, not Streamlit/Gradio.  
**Generated:** 2026-05-25

---

## 0. Project direction

### Repository strategy

Use the existing `kavinravi/finance-dashboard` repository, but treat this as a rebuild rather than a small refactor.

This is better than starting a new repo because:

- The repo name already matches the product.
- It preserves project history.
- The existing code already has useful finance-specific pieces: yfinance fallback fetching, moving averages, RSI, MACD, API-key handling patterns, and data validation ideas.
- The current Streamlit app can be archived under `legacy/` while the new app becomes the primary product.

Recommended migration:

1. Create a branch such as `rebuild-nextjs-mvp`.
2. Move the existing Streamlit app into `legacy/streamlit_app.py`.
3. Move the existing `requirements.txt` into `legacy/requirements.txt`.
4. Create a new monorepo structure with `apps/web` and `apps/api`.
5. Reuse selected analytics logic, but do not preserve the single-file Streamlit architecture.
6. Replace the product frontend with a deployed Next.js app.

A new repository would only be preferable if the current repo had sensitive history, messy unrelated experiments, or if the goal were to preserve the old Streamlit project untouched. For this project, rebuilding in place is the better default.

### Technical direction

Use a **Next.js + TypeScript deployed web app** for the user interface and a separate **Python API/worker** for the pieces where Python is strongest: market-data ingestion, pandas transformations, SEC/XBRL parsing, FinBERT inference, and scheduled summarization.

This gives the project:

- A polished web UI.
- A clean deployed architecture.
- A practical way to run FinBERT without stuffing PyTorch into Vercel serverless functions.
- A migration path from the current repo instead of a full restart.

## 1. Product scope

### Core user flow

The MVP should be built around search, not just a static watchlist.

1. User lands on the dashboard.
2. User searches for a **ticker or company name**.
3. The app resolves the query to a public company/security.
4. The app opens a company research page.
5. The page pulls/caches market data, fundamentals, filings, recent news, FinBERT sentiment, and a `gemini-3-flash-preview` research memo.
6. The user can optionally compare the selected company against **one comparison target**.

### Search examples

- `NVDA`
- `NVIDIA`
- `AMD`
- `Advanced Micro Devices`
- `AAPL`
- `Apple`
- `SPY`
- `SPXT`
- `QQQ`

### Comparison feature

The comparison feature should support one comparison target at a time.

Examples:

- `NVDA` vs `AMD`
- `AAPL` vs `SPY`
- `MSFT` vs `QQQ`
- `TSLA` vs `SPXT`
- Any selected stock vs any ticker/benchmark ETF chosen by the user

Comparison should include:

- Price chart overlay.
- Relative return over selected period.
- Volatility comparison.
- Drawdown comparison.
- Basic performance table.
- Optional side-by-side fundamentals when both assets are operating companies.

### Company research page should show

For the selected company/ticker:

1. Company overview.
2. Price/performance chart.
3. One-target comparison chart.
4. Return metrics: 1D, 5D, 1M, 3M, 6M, YTD, 1Y.
5. Basic technical indicators: moving averages, RSI, MACD, volatility.
6. Fundamentals snapshot.
7. Recent SEC filing metadata where available.
8. Recent news headlines/snippets.
9. Article-level FinBERT sentiment.
10. Aggregate News Tone score.
11. Source-linked daily memo generated by `gemini-3-flash-preview`.
12. Source/provider health and freshness indicators.

### Watchlist role

A watchlist can still exist, but it should be secondary:

- Saved tickers.
- Recent searches.
- Favorite companies.
- Quick access to commonly researched names.

The main product experience should be: **search anything, generate a research page, optionally save it.**

### Non-goals for MVP

- No automated scraping of WSJ, Bloomberg, Morningstar, or other paywalled article bodies.
- No trading execution.
- No portfolio optimization.
- No public redistribution of market data.
- No delisted-company database.
- No “buy/sell/hold” recommendations.

### Compliance/data posture

The MVP should store only what is useful and legally reasonable:

- Article metadata.
- Headlines.
- Snippets/descriptions.
- URLs.
- Source names.
- Ticker tags.
- Provider-returned sentiment fields where available.
- Locally generated sentiment scores.
- LLM summaries of legally accessible metadata/snippets.

For paywalled sources, store links and metadata only unless there is explicit licensed API access or a manual user-provided clipping flow.

## 2. Storage strategy: cache, not warehouse

The project does **not** need a huge database warehouse for the MVP.

The database should be treated as a **bounded cache and analysis store**, not a place where everything piles up forever.

### Why not live-pull everything every time?

Live-pulling everything sounds simpler, but it breaks down quickly:

- Free API quotas are easy to exhaust if every page refresh re-fetches prices, fundamentals, news, and summaries.
- News and fundamentals do not change every second, so repeated live pulls waste API calls.
- FinBERT inference takes time and should not be recomputed unnecessarily.
- Gemini summaries cost latency and possibly money, so they should be cached.
- Without stored daily scores, the app cannot show sentiment trends or “what changed since yesterday?”
- Provider outages would make the app useless if nothing is cached.

### Recommended MVP approach

Use **cache-first with freshness rules**:

| Data type | Freshness rule | Retention |
|---|---|---:|
| Search/company profile | Refresh weekly or when missing | Keep while ticker is saved/recent |
| Daily prices | Refresh after market close or when stale | Long-term; compact and useful |
| Intraday/quote data | Refresh on page load if provider quota allows | Short-term only |
| Fundamentals | Refresh weekly or after filing detection | Long-term selected facts only |
| SEC filing metadata | Refresh daily/weekly | Long-term metadata only |
| News metadata/snippets | Refresh every few hours | 30-90 days |
| Raw provider payloads | Avoid storing, or store briefly for debugging | 1-7 days |
| FinBERT article scores | Compute once per article | Same as article retention, or longer if useful |
| Daily News Tone scores | Compute daily | 6-24 months |
| Gemini daily memos | Generate when new clusters exist | 6-24 months |
| Job/provider health | Store run status/errors | 30-90 days |

### Local vs deployed storage

- **Local development:** SQLite is fine.
- **Deployed MVP:** Postgres is useful if you want persistence across deploys/devices and scheduled background jobs.
- **Cost control:** prune old news and raw payloads. Daily prices and compact score tables are small.

The database should prevent rate-limit waste and preserve computed insights, not become a paid data warehouse.

### Why split JS frontend and Python worker?

Vercel/Next.js is excellent for a polished UI, server-rendered routes, auth, and lightweight API logic. It is not the right place to run PyTorch/Transformers sentiment inference or scheduled ingestion jobs. The Python service can run persistently on Railway, Render, Fly.io, a VPS, or Docker Compose.

### MVP deployment

| Piece | Recommended host | Why |
|---|---|---|
| Frontend | Vercel | Best developer experience for Next.js. |
| Python API/worker | Railway, Render, Fly.io, or small VPS | Persistent process for scheduled jobs and FinBERT inference. |

## 5. Tech stack

### Web app

- **Framework:** Next.js App Router
- **Language:** TypeScript
- **Package manager:** pnpm
- **Styling:** Tailwind CSS
- **Components:** shadcn/ui
- **Charts:** Recharts for standard charts; `lightweight-charts` for candlestick/market-style charts
- **Tables:** TanStack Table
- **Data fetching:** TanStack Query and/or server components calling the backend API
- **Validation:** Zod
- **Auth:** simple password gate for MVP; Supabase Auth/Clerk/Auth.js later
- **Deployment:** Vercel

### Backend / worker

- **Language:** Python 3.12+
- **Package manager:** uv
- **API framework:** FastAPI
- **Async HTTP:** httpx
- **Data validation:** Pydantic v2
- **Database:** SQLite locally; Postgres for deployed persistence
- **ORM:** SQLAlchemy 2.0 or SQLModel
- **Migrations:** Alembic if using Postgres
- **Jobs:** APScheduler for MVP; Celery/RQ later if job volume grows
- **Data processing:** pandas, numpy
- **Sentiment:** Hugging Face Transformers + PyTorch
- **LLM summaries:** Google GenAI SDK using `gemini-3-flash-preview`
- **Testing:** pytest

You are willing to get free API keys, so the MVP should be provider-key friendly from day one.

### Provider notes

#### SEC EDGAR

Use for official U.S. filing/fundamental data.

Endpoints:

```text
https://data.sec.gov/submissions/CIK##########.json
https://data.sec.gov/api/xbrl/companyfacts/CIK##########.json
https://data.sec.gov/api/xbrl/companyconcept/CIK##########/us-gaap/Revenues.json
```

Use cases:

- 10-K/10-Q filing detection.
- Official company facts.
- Revenue, income, cash flow, assets, liabilities, shares, EPS where available.
- Filing links and dates.

#### FMP

Use as the first practical free-key provider.

MVP use cases:

- Ticker/company search.
- Company profile.
- Historical daily prices.
- Basic statements/ratios where free quota allows.
- Financial market news.
- Stock news.

Caveat:

- Watch the daily call budget.
- Keep API calls cached.
- Do not publicly redistribute FMP-sourced data without checking display/licensing terms.

#### Alpha Vantage

Use for:

- News Sentiment endpoint.
- Technical indicators if needed.
- Daily time series fallback.
- Provider sentiment comparison against local FinBERT.

Caveat:

- Free-tier limits can be tight. Build quota-aware scheduling.

#### Finnhub

Use as optional/backup provider:

- Company profile.
- Quote.
- Company news.
- Basic financial metrics.

#### Nasdaq Data Link

Use as optional provider:

- Free/open datasets.
- Dataset experimentation.
- Potential historical/market data endpoints if your account allows.

Caveat:

- Nasdaq Data Link is a marketplace. Some data is free/open; much of the valuable financial data is premium or sample-limited.
- Do not make it the primary MVP dependency unless a specific free dataset matches the app’s needs.

#### yfinance

Use only as fallback/prototype convenience.

Caveat:

- Useful but unofficial.
- Avoid building the deployed app around yfinance if free API-key alternatives are available.

## 10. Data pipeline design

### Pipeline A: search and ticker resolution

Input:

```text
NVIDIA
NVDA
Advanced Micro Devices
SPY
SPXT
```

Steps:

1. Normalize query.
2. Try exact ticker match.
3. Try company-name search through FMP/Finnhub/yfinance fallback.
4. Store recent search.
5. Return candidate matches with ticker, company name, exchange, asset type, and source.

CLI:

```bash
uv run python -m api.worker.cli resolve-query "NVIDIA"
```

### Pipeline B: prices and comparison data

Run cadence:

- On demand when a company page is first opened.
- Daily after market close for saved/recent tickers.
- Avoid intraday real-time for MVP unless needed.

Provider order:

1. FMP Basic if quota available.
2. Alpha Vantage if quota available.
3. Finnhub quote/company endpoints if needed.
4. yfinance fallback.

Steps:

1. Fetch primary ticker daily OHLCV.
2. Fetch comparison ticker daily OHLCV if selected.
3. Upsert into `price_bars_daily`.
4. Compute:
   - 1D return.
   - 5D return.
   - 1M return.
   - 3M return.
   - 6M return.
   - YTD return.
   - 1Y return.
   - 10/20/50-day moving averages.
   - RSI.
   - MACD.
   - 5-day volatility.
   - Relative return versus comparison target.
5. Store technical indicators separately.

CLI:

```bash
uv run python -m api.worker.cli fetch-prices --ticker NVDA --comparison AMD --lookback 400d
```

### Pipeline C: fundamentals and filings

Run cadence:

- On demand when a company page is first opened.
- Weekly for saved/recent tickers.
- After detected 10-K/10-Q/8-K events.

Provider order:

1. SEC EDGAR official company facts.
2. FMP normalized ratios if quota allows.
3. Alpha Vantage fundamentals fallback.
4. Finnhub metrics fallback.

Steps:

1. Use SEC submissions endpoint to detect recent filings.
2. Pull CompanyFacts for each CIK.
3. Extract minimal facts:
   - Revenue.
   - Net income.
   - Operating income.
   - EPS diluted.
   - Assets.
   - Liabilities.
   - Stockholders equity.
   - Operating cash flow.
   - Capital expenditures where available.
4. Store raw facts with metadata.
5. Compute derived metrics later.

### Pipeline D: news ingestion

Run cadence:

- On demand when a company page is opened and cache is stale.
- Every 2-4 hours for saved tickers on market days if quotas allow.
- Daily for first MVP if quotas are tight.

Provider order:

1. FMP Stock News.
2. Alpha Vantage News Sentiment.
3. Finnhub Company News.
4. Yahoo Finance RSS/link-only fallback.
5. Nasdaq Data Link only if a specific free dataset/endpoints fit the need.

Steps:

1. For the selected ticker, call enabled news providers.
2. Normalize provider responses into `ArticleIn`.
3. Canonicalize URL.
4. Hash title + source + published date.
5. Upsert article.
6. Store provider sentiment fields when available.
7. Set `expires_at` for retention pruning.
8. Track provider calls and errors in `provider_accounts`/`job_runs`.

Normalized schema:

```python
class ArticleIn(BaseModel):
    source: str
    source_article_id: str | None = None
    canonical_url: str
    title: str
    snippet: str | None = None
    published_at: datetime
    tickers: list[str] = []
    provider_sentiment_score: float | None = None
    raw_payload: dict | None = None
```

### Pipeline E: deduplication

Run after news ingestion.

MVP dedupe stages:

1. Exact URL match.
2. Normalized title hash.
3. Fuzzy title similarity.
4. Date bucket + ticker match.

MVP cluster ID:

```text
cluster_id = sha256(
  normalized_title_without_source_words
  + primary_ticker
  + published_date_bucket
)
```

Later:

- Use embeddings.
- Use MinHash/SimHash.
- Cluster syndicated copies more aggressively.

### Pipeline F: FinBERT sentiment scoring

Model options:

1. `yiyanghkust/finbert-tone`
2. `ProsusAI/finbert`

Input text:

```text
{headline}

{snippet}
```

Output:

```json
{
  "positive": 0.71,
  "neutral": 0.21,
  "negative": 0.08,
  "sentiment_score": 0.63,
  "label": "positive",
  "confidence": 0.71
}
```

Formula:

```text
sentiment_score = positive_probability - negative_probability
```

Labeling:

```text
if sentiment_score >= 0.20 and confidence >= 0.50: positive
elif sentiment_score <= -0.20 and confidence >= 0.50: negative
else: neutral
```

Important:

- Call this **News Tone**, not “Investment Outlook.”
- FinBERT tone is not the same as stock impact.
- Later add event/business-impact classification.

### Pipeline G: daily company scoring

For each ticker/date:

1. Get deduplicated recent articles.
2. Weight article sentiment by:
   - Relevance to ticker.
   - Source reliability.
   - Recency decay.
   - Sentiment confidence.
3. Aggregate into a dashboard score.

MVP formula:

```text
article_weight =
  relevance_score
  * confidence
  * source_weight
  * exp(-age_hours / 36)

weighted_sentiment =
  sum(sentiment_score * article_weight) / sum(article_weight)

dashboard_score =
  round(50 + 50 * weighted_sentiment)
```

Display ranges:

```text
0-30: bearish/news-risk heavy
31-45: somewhat negative
46-55: neutral/mixed
56-70: somewhat positive
71-100: bullish/news-positive
```

### Pipeline H: `gemini-3-flash-preview` summaries

Run cadence:

- On demand when a company page is opened and the digest is stale.
- Once per day for saved tickers after news ingestion.
- Avoid re-summarizing unchanged article clusters.

Model:

```bash
GEMINI_MODEL=gemini-3-flash-preview
GEMINI_FALLBACK_MODEL=gemini-3.5-flash
```

Input:

- Deduped articles.
- Article IDs.
- Headlines.
- Snippets.
- Source names.
- Published timestamps.
- Price move context.
- Comparison context if selected.
- Recent filing/fundamental events.
- Existing sentiment score.

Output schema:

```json
{
  "ticker": "NVDA",
  "date": "2026-05-25",
  "one_sentence_takeaway": "...",
  "bullish_developments": [
    {
      "claim": "...",
      "why_it_matters": "...",
      "source_article_ids": ["..."],
      "confidence": "medium"
    }
  ],
  "bearish_developments": [],
  "neutral_or_operational_updates": [],
  "comparison_context": {
    "comparison_ticker": "AMD",
    "relative_performance_summary": "...",
    "confidence": "medium"
  },
  "market_reaction": {
    "price_move": "...",
    "possible_explanation": "...",
    "confidence": "low"
  },
  "watch_items": [],
  "contradictions_or_caveats": [],
  "overall_news_tone": {
    "label": "mixed-positive",
    "score": 62,
    "rationale": "..."
  }
}
```

Prompt rules:

- Never output “buy,” “sell,” or “hold.”
- Cite source article IDs for each claim.
- Distinguish confirmed company events from analyst speculation.
- Say when evidence is weak, duplicated, stale, or sparse.
- Do not imply access to full paywalled article text.
- Prefer “what changed” over generic company description.
- Do not invent facts missing from the snippets/metadata.

## 15. Risk register

| Risk | Severity | Mitigation |
|---|---:|---|
| Paywalled-source scraping violates terms | High | Do not scrape. Link out or use licensed APIs/manual clipping. |
| Free API quotas are too low | Medium | Cache-first design, quota manager, source priority, paid FMP upgrade only if useful. |
| Database grows too much | Medium | Retention policies, prune old news/raw payloads, keep prices/scores compact. |
| Vercel serverless unsuitable for FinBERT | High | Run FinBERT only in Python worker service. |
| yfinance fragility | Medium | Use as fallback only. |
| Misleading sentiment score | High | Label as News Tone, show article count/confidence/evidence. |
| LLM hallucination | High | Use structured output, source IDs, and strict prompt rules. |
| SEC XBRL normalization is messy | Medium | Start with minimal concepts; use FMP normalized fields as fallback. |
| Duplicate articles distort sentiment | Medium | Deduplicate before summaries and daily scoring. |
| Dad distrusts summaries | Medium | Every claim links to source articles and confidence labels. |
